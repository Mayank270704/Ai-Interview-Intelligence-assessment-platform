# Adaptive interview baseline

Offline experiment. **Not part of the product.** The interview still decides
difficulty exactly as it always has — through the Interviewer Brain — and no API
response is derived from anything here.

## What it predicts

`InterviewDecision.difficulty_direction`: whether the interviewer intends the
next question to be **harder**, **easier**, or held at the **same** level.

This target was chosen because it is a genuine judgement rather than a
restatement of arithmetic the codebase already performs. The final assessment
score, by contrast, is computed in closed form by `app.ai.assessment.scorer`, so
a model predicting it would only be memorising a formula.

Note the label is the interviewer's *intent*, not its clamped effect:
`InterviewTurnService._select_difficulty` is what clamps "increase" at `hard`.

## Features

31 structured signals per turn — 15 closed-vocabulary categories and 16 counts,
one-hot encoded and scaled into 94 columns by `app.ml.encoding`.

| Group | Signals |
| --- | --- |
| Question | difficulty, interviewer intent, evaluation-focus count, turn number |
| Answer analysis | correctness, reasoning quality, relevance, depth, completeness, and counts of demonstrated / missing / incorrect concepts and unsupported claims |
| Evaluation | correctness, conceptual understanding, completeness, depth, reasoning, relevance, application ability, confidence, and counts of evidence / gaps / strengths |
| Knowledge state | concepts tracked / demonstrated / missing / incorrect, claims supported / unsupported / uncertain |

No question text, answer text, transcript, concept name, claim name, identity,
audio, or video is used. See `app/ml/schema.py` for why each is excluded.

## Reproducing

```bash
python ai-lab/experiments/adaptive_interview/train_baseline.py
```

Deterministic for a given seed. Outputs land in `ai-lab/datasets/` and
`ai-lab/evaluation/` and are gitignored, since they regenerate exactly.

## Results (synthetic data, seed 20260903)

1457 examples from 220 generated interviews; 1092 train / 365 validation,
stratified.

| Metric | Model | Majority-class baseline |
| --- | --- | --- |
| Accuracy | 0.836 | 0.608 |
| Macro F1 | 0.817 | 0.252 |
| Balanced accuracy | 0.836 | 0.333 |

Per-class F1: decrease 0.763, maintain 0.859, increase 0.828.

Accuracy alone flatters any model here — `maintain` is 61% of rows — so macro F1
and balanced accuracy are the metrics that matter, and both show the minority
movements are actually being detected rather than ignored.

## What these numbers do and do not mean

**They mean** the feature contract, encoder, and training pipeline work end to
end, and that the structured signals carry enough information to recover a
latent competence judgement through noisy observations. The generator draws a
hidden ability per interview and samples the observable features *around* it, so
the model has to infer rather than read the answer off one column — which is why
accuracy sits near 0.84 rather than at 1.0.

**They do not mean** the model is accurate on real interviews. It has never seen
one. The scenarios were generated by a policy in `app/ml/synthetic.py`, and a
model that recovers that policy has demonstrated the plumbing works, not that it
has learned how real interviewers behave.

Real-world performance is **currently unknown and unmeasured**. Establishing it
needs consented real interview data (`--source consented`), which does not exist
yet.
